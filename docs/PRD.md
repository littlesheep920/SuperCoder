## 1. 产品定位（不变）

SuperCoder 是**面向企业研发流程的 AI 能力资产治理与编排平台**。

它管理的不是"模型调用"，而是**能力资产**：企业到底有哪些可复用的 AI 能力、谁维护、什么版本、能用在什么场景、需要什么权限、能不能组合成一条研发流水线、用完之后效果如何。

### 1.1 核心问题

| 痛点 | 表现 |
|---|---|
| 能力看不见 | 各团队各建各的 Skill/Prompt/Agent，无人知道彼此存在 |
| 能力找不到 | 工程师只能靠记忆和口口相传，无法用业务语言检索 |
| 能力判不了 | 不知道某个能力是否经过审核、依赖是否满足、权限是否够 |
| 能力连不起来 | 单个能力无法完成"需求分析→代码审查→测试生成"的完整链路 |
| 能力管不住 | 谁在用什么版本、执行了什么、结果如何，全无审计 |
| 重复建设 | 同一个能力被 5 个团队各写一遍 |

### 1.2 一句话价值主张

> **让企业的 AI 能力能被看见、找到、判断、组合、审批、执行、追踪、评测。**

## 2. 核心设计原则（不变，且已被 Stage 1 验证）

这六条**不因任何纠偏而放宽**：

1. **事实源分离**：Git 存资源正文（事实源），MySQL 存治理元数据（事实源）。Qdrant/Redis **只是可重建的派生索引**，不承载任何权威。
2. **LLM 不越权**：模型可以理解、解释、草拟；**不能**决定权限、发布、审批、任务是否完成。
3. **`202 Accepted` ≠ 完成**：只表示意图已持久化，最终结果只能读 Job 状态和事件流。
4. **默认离线、默认全禁用**：`LLM_ENABLED=false`、外部调用默认关闭；未启用组件**不读取对应密钥**。
5. **失败即停止（fail-closed）**：不确定时拒绝，不降级为"看起来成功"。
6. **四态验收**：`PASS / FAIL / NOT RUN / HOLD`，**HOLD 必须写明原因，禁止伪报为 PASS**。

## 3. 本次重置的五项根本性改变

这是 PRD V2.0 与 V1.0 的**本质区别**，也是纠偏的落地。

### 3.1 改变一：用"未开始 / 进行中 / 已完成"取代"完整建设原则"

**V1.0 的问题**：§2.3 宣称"阶段不代表功能缩水"，导致 Stage 1 验收时就被要求具备 Stage 5 的能力，逻辑上不可能满足。

**V2.0 的定义**：

| 状态 | 含义 | 允许 |
|---|---|---|
| **未开始** | 本阶段范围之外 | ✅ 允许，但**不得**声称已完成 |
| **进行中** | 已进入实现，但边界功能未齐 | ⚠️ 允许交付，必须标注缺口 |
| **已完成** | 范围内功能 + 异常路径 + 测试 + 文档齐备 | ✅ 可声称完成 |

**唯一禁令（对应 R-1）**：
> 凡声称"已完成"的功能，**不得**使用静态占位页、假数据按钮、只能看不能操作的演示、或永久 Mock 来代替真实实现。

**不是禁令**：本阶段没排的功能，就是"未开始"。这**不是缩水，也不是失败**。

### 3.2 改变二：用"指标报告"取代"指标门禁"

**V1.0 的问题（R-2 死锁）**：进 Stage 2 需 100 条人工标注查询 → 标注查询需可检索资源库 → 资源库是 Stage 2 产物。**闭环，靠努力无法突破。**

**V2.0 的规则**：

| 阶段门禁检查 | 不检查 |
|---|---|
| ✅ 评测**已运行** | ❌ 指标是否达标 |
| ✅ 原始结果**已归档**（每条查询的召回、排名、耗时） | ❌ 是否达到某个数字 |
| ✅ 数据集版本/hash、代码版本、配置、种子**已记录** | — |
| ✅ 与基线对比**已生成** | — |

**数值目标改为季度目标，不绑定阶段流转**，见 §7。

**理由**：指标是"改进的度量"，不是"进度的闸门"。用不可达的数字卡住阶段，只会逼人造假——而造假的代价正是这个项目最想避免的。

### 3.3 改变三：基础设施按"规模触发"，默认最小化

**V1.0 的问题（T-1）**：Demo 规模（≤120 资源、≤4 Worker、单机）却要求 MySQL + Redis + Qdrant + RocketMQ 四套有状态服务，这会让整条链路都依赖开发机上不存在的服务。

**V2.x 的规模阈值表**：

| 组件 | 状态（V2.2 实测） | **启用阈值** | 阈值以下用什么 |
|---|---|---|---|
| MySQL 8 | ✅ **已实现并验证**（8.0.40，22 张表） | — | 唯一必需的有状态服务 |
| **向量检索** | ✅ **已实现**：进程内 `numpy` 矩阵 | 单资源库 > **2,000** 个已发布版本 | 当前方案本身 |
| **Qdrant** | ❌ **完全未实现**（仅有配置开关，无客户端代码） | 同上一行 | 不需要 |
| **Redis** | ❌ **完全未实现**（仅有配置开关，无客户端代码） | Worker > **4**，或需跨机协调、分布式锁 | MySQL `FOR UPDATE SKIP LOCKED` 轮询 |
| **RocketMQ** | ❌ **完全未实现** | 需跨机可靠投递 + 死信追踪 | MySQL `job` 表 + 状态机 |
| **外部 Embedding/Rerank** | ✅ **已实现并验证**（SiliconFlow，默认关闭） | 需语义检索/质量评测 | `local-hash`（仅验证管线，无语义能力） |

> **重要澄清（V2.2）**：`SUPERCODER_QDRANT_ENABLED` 与 `SUPERCODER_REDIS_ENABLED` 是**预留的配置开关**，
> 打开它们**不会**让系统连接 Qdrant 或 Redis —— 因为没有任何客户端代码。
> 之前版本把这两项描述为"默认不启用"，容易被误读为"已实现、只是关着"。实际是**未实现**。
> 若将来需要，应按 Provider 接口先写适配器，再打开开关。

**强制规则**：
- **Provider 接口先写，实现后补**。任何组件都必须能在"未启用"状态下让全链路跑通。
- 阈值是**工程判断，可用实测数据推翻**，但推翻需在文档里记录依据。
- **配置开关的存在不代表能力的存在**。文档描述组件状态时必须区分「已实现但关闭」与「未实现」。

**已验证的直接收益**：Stage 2 检索**只依赖 MySQL + 可选的外部 Embedding API**，
在无 Qdrant、无 Redis 的情况下完成了全部功能与评测（见 `docs/STAGE2_ACCEPTANCE_REPORT.md`）。

### 3.4 改变四：资源分档，禁止用总量掩盖质量

**V1.0 的问题（R-4）**：要求 120 项"真实"资源，但真实的 Agent / Workflow 资源在企业外几乎不存在，与"禁止凑数"直接冲突。

**V2.0 的三档定义**：

| 档位 | 定义 | 可验证性 |
|---|---|---|
| `reference` | 可溯源到公开仓库 / 官方规范 / 真实产品 | 必须有来源 URL + 版本 |
| `example` | 平台自建，用于演示与测试 | 必须**明确标注**非生产 |
| `enterprise` | 企业内部导入 | 不入公开仓库，仅记数量 |

**报告规则（强制）**：
> 任何对外材料**禁止**把三档合计成一个数字。必须写成：`共 N 项（reference A / example B / enterprise C）`。

### 3.5 改变五：补充资源假设，明确"谁在什么条件下能完成"

**V1.0 的问题（R-6）**：全文无工期、人月、预算，却要求 500+ 人工标注样本。

**V2.0 的三种路线图**（§8），并明确标注**单人不可执行的门禁**。

## 4. 用户与场景

### 4.1 角色

| 角色 | 核心诉求 | 关键权限 |
|---|---|---|
| **能力所有者**（Owner） | 登记、迭代自己的能力 | 创建、编辑草稿、提交审核 |
| **审核者**（Reviewer） | 把关质量与安全 | 批准 / 要求修改 |
| **发布者**（Publisher） | 控制上线节奏 | 发布、下架、回滚 |
| **工程师**（Consumer） | 用业务语言找到并组合能力 | 检索、查看、发起 Workflow |
| **多角色兼任** | 小团队里同一人常同时是 owner + reviewer + publisher | 权限取并集，按团队生效 |

> 角色与权限的**权威定义**在 `docs/RESOURCE_GOVERNANCE.md`，本文不复述。
>
> **注意**：V1.0 曾设有独立的"平台管理员"角色。V2.0 取消该角色——见 §4.3。

### 4.2 首要场景（P0）

> 工程师提需求 → 系统找到候选能力 → 工程师确认 → 组合成 Workflow → 人工审批 → 异步执行 → 产出工程报告 → 数据回流。

### 4.3 身份与界面门控：能力驱动，不做 admin/user 分裂

**这是本文对 V1.0 的一处澄清**（原计划未定义界面角色模型，实现中遗漏）。

#### 4.3.1 为什么不做"admin 后台 + user 前台"

| 理由 | 说明 |
|---|---|
| **模型不匹配** | 本产品的权限是 `namespace:action` 细粒度声明 + 团队绑定的治理角色，不是"管理员/普通用户"二元。强行二分会把所有者对自有资源的自治能力削掉。 |
| **已用三处页面切开** | 资源治理、审核、发布是**三套不同语境的操作**，分属列表/详情、审核页、发布动作，不是两个界面能承载的。 |
| **admin 会成为第二授权系统** | 一旦出现"全局管理员"页面，就会诱导把权限判断写进前端，与"服务端授权是唯一权威"冲突。 |
| **安全上无收益** | 后端已强制校验（`governance.py` 4 处角色判定 + `test_member_cannot_publish`）。隐藏按钮从来不是安全边界。 |

#### 4.3.2 采用的能力驱动门控

**唯一权威仍在服务端**。前端只做**可用性提示**：

```text
GET /v1/auth/me
→ {
    subject_id, display_name,
    teams: [...],
    governance_roles: ["owner", "reviewer"],     # 已在实现中存在于 AuthContext
    capabilities: ["resource:read", "resource:write", "review:publish", ...]
  }
```

- `capabilities` 是**服务端计算的并集结果**，前端不得自行推导或扩展。
- 前端用它决定：显示/隐藏操作按钮、禁用无权输入、展示角色徽标、选择空态文案。
- **任何按钮门控都不得替代服务端校验**。若前端显示可点但服务端拒绝，视为**前端缺陷**（体验 bug），不是安全事件。
- 无 `capabilities` 时前端必须**fail-closed**：按最小权限渲染（只读）。

#### 4.3.3 差异化的具体范围

| 界面区域 | 依据 | 变化 |
|---|---|---|
| 资源列表 | `resource:write` + 是否本团队 | 显示"编辑/新建"入口，否则只读 |
| 资源详情 | 同上 | "提交审核"按钮可见性 |
| 审核页 | `reviewer` / `validator` | "批准""要求修改"可见性 |
| 发布动作 | `publisher` | "发布""下架""回滚"可见性 |
| 任务页 | 服务端已按可见性过滤 | 无需前端判断，只渲染返回结果 |
| 审计页 | `audit:read` | 入口可见性 |
| 全局 | `capabilities` 缺失 | 全部按只读渲染 |

#### 4.3.4 明确不做的部分

- ❌ 不做独立的"系统管理后台"（用户/团队/配置 CRUD 页面）。
  **理由**：用户与团队来自目录同步（OIDC/AD），平台不拥有它们，无法也不应提供 CRUD。
- ❌ 不做"切换身份"的调试开关进入生产。
- ❌ 不改动任何现有后端授权逻辑——本次只是把已有事实暴露给前端。

> **实现状态**：后端角色判定**已完成**并有测试；`/v1/auth/me` 与前端门控**未开始**，见 §5.8。

## 5. 功能范围与优先级

优先级定义：**P0 = 没有它产品不成立；P1 = 显著提升价值；P2 = 锦上添花**。

> **契约覆盖度（V2.2 实测）**：冻结的 `openapi.stage0.yaml` 定义了 **29 个操作**，
> 当前实现 **23 个路由**，其中**匹配契约的 16 个（55%）**。
> 另有 7 个已实现但不在冻结契约中的扩展端点（`/health`、`/ready`、`/audit`、`/diff`、`/rollback`、`/retry`、`DELETE /resources/{id}`）。

> 以下三个功能域**完全未实现**，属未开始，不是缩水：
> `agent-registrations`（4 个操作）、`workflows`/`workflow-runs`（7 个操作）、`evaluations`（3 个操作）。

## 6. 明确不做（Non-Goals）

写清楚"不做什么"与"做什么"同等重要：

| 不做 | 理由 |
|---|---|
| 通用 LLM 聊天机器人 | 本产品是**资产治理**，不是 chat |
| 让模型决定权限/发布/审批 | 违反核心原则 2 |
| 平台内托管用户的 API Key | 违反安全契约，密钥只从环境注入 |
| 在用户机器上启动 Cursor/Dify | 平台无法控制，见 §5.6 |
| 用户名密码注册登录 | 见 §5.7 |
| **独立的 admin 管理后台（用户/团队/配置 CRUD）** | 用户与团队来自目录同步，平台不拥有它们；且会诱导把权限判断写进前端，见 §4.3.1 |
| **把界面裂成"admin 端 / 用户端"两套** | 权限是细粒度声明 + 团队绑定角色，不是二元；见 §4.3.1 |
| **前端推导或扩展 capabilities** | 只能消费服务端结果，见 §4.3.2 |
| 为凑数生成 120 项假资源 | 见 §3.4 |
| 用 Mock 冒充已完成功能 | 见 §3.1 唯一禁令 |
| 追求"零依赖"而手写图编辑器 | 时间应花在执行链路，见 §5.5 |
