# SuperCoder 产品需求文档

---

## 1. 产品定义

### 1.1 一句话

SuperCoder 是面向企业研发团队的 **AI 能力资产治理与检索平台**。

### 1.2 解决的问题

企业内部的 AI 能力（提示词、技能、Agent、MCP 服务、工具、工作流）正在快速积累，但缺乏统一治理，导致六类问题：

| 问题 | 具体表现 |
|---|---|
| 看不见 | 各团队各建各的，无人知道彼此存在 |
| 找不到 | 只能靠记忆和口口相传，无法用业务语言检索 |
| 判不了 | 不知道某个能力是否通过审核、依赖是否满足、权限是否足够 |
| 连不起来 | 单个能力无法完成"需求分析 → 代码审查 → 测试生成"的完整链路 |
| 管不住 | 谁在用哪个版本、执行了什么、结果如何，全无审计 |
| 重复建设 | 同一能力被多个团队重复实现 |

### 1.3 产品边界

SuperCoder **不是**：

- 通用 LLM 对话产品——它管理的是能力资产，不是聊天
- 模型网关——它不代理模型调用，也不托管凭据
- 代码仓库——能力正文存放在 Git，但平台本身不是 Git 服务

### 1.4 核心价值

> 让企业的 AI 能力**能被看见、找到、判断、审批、追踪、评测**。

## 2. 核心设计原则

以下六条是架构约束，任何实现选择都不得违反。

### 2.1 事实源分离

| 存储 | 承载什么 | 丢失后果 |
|---|---|---|
| **Git** | 能力正文、脚本、配置、版本快照 | 事实源，不可恢复 |
| **MySQL** | 身份、版本、生命周期、权限、审核、任务、审计 | 事实源，不可恢复 |
| 检索索引 | 由 Git 内容 + MySQL 元数据派生 | 重建即可 |
| 缓存 | 加速查询 | 清空即可 |

派生索引和缓存**不承载任何权威**。索引与 MySQL 记录不一致时，停止使用索引并重建。

### 2.2 模型不参与治理决策

大模型可以：理解需求、解释结果、生成草稿、比较候选。

大模型**不可以**单独决定：权限、发布、审批、任务是否完成。

这些决策只能由确定性代码 + 数据库约束 + 人工审批完成。检索分数、模型输出、缓存内容都必须在返回前对照当前事实重新验证。

### 2.3 异步不等于完成

接口返回 `202 Accepted` 只表示**意图已被持久化**。任务的真实结果只能通过查询任务状态与事件流获得。

### 2.4 默认安全

- 外部服务（模型、向量库、缓存）**默认全部关闭**
- 未启用的组件**不读取对应凭据**
- 缺少必需凭据时启动失败，不降级到默认值或匿名访问
- 不确定时拒绝，而不是"看起来成功"

### 2.5 可验证性

任何能力声明必须可追溯到命令、产物或测试。状态只有四种：

| 状态 | 含义 |
|---|---|
| **PASS** | 已执行且通过 |
| **FAIL** | 已执行但未通过 |
| **NOT RUN** | 未执行 |
| **HOLD** | 环境不具备，**必须写明缺什么** |

禁止把 HOLD 表述为 PASS，禁止用占位页、假数据或永久 Mock 冒充已实现。

### 2.6 阶段是范围边界，不是质量折扣

| 状态 | 定义 |
|---|---|
| **未开始** | 尚无代码 |
| **进行中** | 已有实现，范围内功能未齐 |
| **已完成** | 功能 + 异常路径 + 测试 + 文档齐备 |

范围内未排期的功能就是"未开始"，这是正常状态。但**一旦声称"已完成"，就必须达到完整质量**。

## 3. 用户与权限

### 3.1 角色

权限是**细粒度的 `namespace:action` 声明**，绑定到团队，而非二元的管理员/普通用户。

| 角色 | 职责 | 关键权限 |
|---|---|---|
| 能力所有者 | 登记与迭代自己的能力 | 创建、编辑草稿、提交审核 |
| 审核者 | 把关质量与安全 | 批准、要求修改 |
| 发布者 | 控制上线节奏 | 发布、下架、回滚 |
| 工程师 | 查找并使用能力 | 检索、查看、发起流程 |
| 多角色兼任 | 小团队常见形态 | 权限取并集，按团队生效 |

### 3.2 权限模型

有效权限是**多层求交**的结果：

```
调用者授权 ∩ 平台策略 ∩ 资源声明 ∩ 依赖声明 ∩ 当前审批
```

显式拒绝（`deny`）永远优先于允许。资源清单中的 `permissions` 只是**声明**，不构成授权。

### 3.3 可见性

可见性（私有 / 团队 / 组织 / 公开）由服务端根据调用者身份与团队关系推导，**在数据库查询层过滤**，先于计数、排序和分页。

### 3.4 界面门控

界面**不做管理员端与用户端的分裂**。权限模型是细粒度声明，强行二分会削掉所有者对自有资源的自治能力。

界面采用**能力驱动门控**：

- 服务端在 `GET /v1/auth/me` 返回调用者的能力集合（`capabilities`）
- 前端据此显示或隐藏操作入口
- **按钮门控不构成安全边界**，服务端授权始终是最终判定
- 能力集合缺失、为空或加载失败时，界面按只读渲染

**单一事实源**：能力集合由 `apps/api/domain/capabilities.py` 推导，其角色谓词与治理服务共用同一套函数，不存在第二份规则副本。

**一致性保证**：`GatedOperation` 声明每个受控操作需要哪个能力；测试遍历全部 16 种角色组合 × 12 个受控操作，断言「能力存在」与「服务端放行」双向一致。

> 当前状态：服务端权限强制、`capabilities` 接口、前端门控**均已实现并验证**（见 §11）。

## 4. 领域模型

### 4.1 六类资源

| 类型 | 定义 | 核心要素 |
|---|---|---|
| **Skill** | 面向 Agent 的工作方法与步骤 | 适用场景、执行步骤、输入输出、限制 |
| **MCP** | 提供工具或数据访问的 MCP Server | 传输方式、工具列表、参数 Schema、权限 |
| **Prompt** | 可复用的提示词或模板 | 模板正文、变量、输出格式、适用模型 |
| **Agent** | 带角色、模型、工具和规则的智能体 | 角色、目标、工具、权限、安全边界 |
| **Workflow** | 多个资源组成的研发流程 | 节点、连线、条件、重试、审批 |
| **Tool** | 确定性代码工具或企业接口 | 入口、参数 Schema、返回 Schema、执行方式 |

### 4.2 生命周期

资源以 `(类型, 标识, 版本)` 为单位独立治理，七个状态：

| 状态 | 含义 | 可执行性 |
|---|---|---|
| `draft` | 编写中 | 仅所有者可见 |
| `validating` | 自动检查中 | 仅隔离环境 |
| `pending_review` | 等待人工审核 | 只读 |
| `approved` | 已通过审核，未发布 | 可演练 |
| `published` | 已发布，内容不可变 | 满足条件可执行 |
| `deprecated` | 保留但不再推荐 | 存量可用，新增不再指向 |
| `retired` | 已退出服务 | 仅保留审计 |

状态转换有严格的合法性矩阵，同状态写入只能作为幂等重放。

### 4.3 版本与内容

- 版本遵循语义化版本（SemVer）
- 已发布版本**内容不可变**；需要修改必须发布更高版本
- 回滚**不会**修改历史版本，而是基于历史快照创建更高的新版本
- 依赖必须固定到精确版本，不允许隐式升级

### 4.4 内容哈希

| 哈希 | 计算范围 | 何时变化 |
|---|---|---|
| `artifact_hash` | 清单（排除 `status`）+ 入口 + 全部受管文件 | 内容变化时 |
| `manifest_snapshot_hash` | 完整清单（含 `status`） | 每次状态变化 |

检索命中的每条结果都必须携带 `artifact_hash`，以确保结果可追溯到确切的不可变内容。

| 能力 | 优先级 | 状态 |

**检索链路**：

```
结构化过滤（权限前置）
    ↓
┌─────────────┬─────────────┐
│ BM25 关键词  │ 向量语义     │
└─────────────┴─────────────┘
    ↓
RRF 融合
    ↓
交叉编码器精排（可选）
    ↓
返回（每项带内容哈希与各路分数）
```

**中文检索策略**：中文按字符二元组切分，英文与代码标识符按词切分。二元组避免单字导致的 IDF 失效，也不需要维护词典；精确术语由关键词路负责，语义匹配由向量路负责，两路互补。

**降级规则**：语义检索不可用时，混合模式退化为纯关键词；语义模式回退关键词。降级**必须在响应中显式上报**，不得静默。

### 5.3 能力发现 Agent

| 能力 | 优先级 | 状态 |
|---|---|---|
| 查询约束抽取 | P0 | 已实现并验证 |
| 推荐理由生成（附来源与版本） | P0 | 已实现并验证 |
| 无证据时拒答 | P0 | 已实现并验证 |
| 缺失信息追问 | P1 | 已实现并验证 |
| 自然语言登记草稿 | P1 | 已实现并验证 |
| 重复建设识别 | P1 | 未开始 |

**安全约束**：Agent 只能使用检索接口返回的候选，不得直接查询数据库；资源正文视为不可信数据，不构成指令。

**两个通道是分开的端点**：

| 通道 | 端点 | 做什么 | 不做什么 |
|---|---|---|---|
| 发现 | `POST /v1/discovery/recommend` | 在调用者可见的候选内判断相关性，给出带来源与哈希的推荐，或带证据的拒答 | 不扩宽候选范围、不判断权限、不发布 |
| 登记 | `POST /v1/registration/draft` | 把自然语言描述变成候选 manifest，并用与 CI 相同的 schema 校验 | **不写入任何数据**、不创建资源、不审批 |

**拒答不依赖分数阈值**。实测（`docs/RETRIEVAL_SCORE_ANALYSIS.md`）：

- 查询内部：相关结果的分数高于不相关结果的比例为 **89.3%**，排序有效
- 查询之间：无相关结果的查询最高 top-1 为 **0.9582**，可回答查询最低为 **0.0007**，完全交叠

若按阈值拒答，会把 94.6% 的可回答查询误拒。因此拒答由模型显式判断，且必须列出它考虑过的候选（`considered`），使拒答可被核查。

**模型不能扩大候选范围**：推荐的 `resource_id` / `version` / `artifact_hash` 一律由服务端从先前的检索结果回填；模型给出列表中不存在的 id 时，该条被丢弃，若全部无效则降级为拒答（`model_cited_no_valid_candidate`）。

**登记草稿的错误率实测**（同一描述，三次提示词迭代）：

| 提示词形态 | schema 错误数 |
|---|---|
| 散文式字段说明 | 11 |
| 单一 kind 骨架 | 5 |
| 骨架 + 其余 kind 的必需键摘要 | **0** |

提示词骨架由 `schemas/resource.schema.json` 派生，schema 变更会同步反映到提示词。

**登记的三段式**（决定 → 预演 → 写入）：

| 阶段 | 端点 | 是否写数据 | 说明 |
|---|---|---|---|
| 生成草稿 | `POST /v1/registration/draft` | 否 | 模型生成候选 manifest，复用 CI 校验器 |
| 预演差异 | `POST /v1/registration/preview` | 否 | 给出与既有同名资源的差异，供人工判断 |
| 确认提交 | `POST /v1/registration/commit` | **是** | 必须 `confirmed: true`；写入 Git 后登记 |

**登记草稿的安全约束**：

- 模型输出的 `status` 一律被强制改写为 `draft`，生成物不可能以已发布状态出现
- 校验复用与 CI 相同的校验器，不是另一套更宽松的规则
- `draft` 与 `preview` 只读；只有 `commit` 写数据，且必须携带 `confirmed: true`
- `commit` 在写入前**重新校验**草稿，不信任浏览器里几分钟前的校验结果
- 写入失败时清理已写文件，避免出现"有目录但没有治理记录"的半成品
- 无 MySQL 或 Git 只读时，`commit` 直接返回 503，不会假装写入成功
- 无模型时直接返回 `llm_unavailable`，不用模板拼凑一个看起来可用的草稿

## 6. 不做的事

| 不做 | 理由 |
|---|---|
| 通用 LLM 对话产品 | 本产品治理能力资产，不是聊天 |
| 让模型决定权限或发布 | 违反核心设计原则 |
| 在平台内托管用户的 API Key | 凭据只从环境注入 |
| 在用户机器上启动 Cursor/Dify | 平台无法控制 |
| 用户名密码注册登录 | 身份来自企业目录，平台不拥有密码 |
| 独立的管理员后台 | 用户与团队来自目录同步，且会诱导把权限判断写进前端 |
| 前端推导或扩展能力集合 | 只能消费服务端结果 |
| 为凑数生成虚假资源 | 损害项目诚信 |
| 用占位页或 Mock 冒充已实现 | 违反可验证性原则 |

## 7. 质量指标

### 7.1 分层

| 层 | 指标 | 用途 |
|---|---|---|
| **正确性**（门禁） | 评测可运行、结果可复现、原始数据完整 | 决定能否流转 |
| **质量**（目标） | 检索命中率、排序质量、推荐采纳率 | 衡量改进 |
| **性能**（观测） | 延迟分位数、任务成功率 | 发现退化 |

正确性是门禁；质量与性能是**报告**，不作为流转的前置条件。用不可达的数字卡住阶段，只会逼人造假。

### 7.2 检索质量实测

评测集：**301 条中文业务语言查询，290 项示例资源，852 条标注，单标注者。**

语料覆盖六类资源、14 个团队、5 种运行时。除 6 项早期 `demo-` 资源外，其余全部以 `example-` 前缀与标签标注，描述首句声明为示例内容。

| 模式 | Hit@5 | MRR@10 | NDCG@10 | P95 延迟 |
|---|---|---|---|---|
| 纯关键词 | 0.100 | 0.098 | 0.076 | 121 ms |
| **混合（默认）** | **0.944** | **0.856** | **0.706** | **523 ms** |
| 纯语义 | 0.937 | 0.856 | 0.704 | 553 ms |

**指标随语料规模的变化**：

| 语料 / 查询 | 关键词 Hit@5 | 混合 Hit@5 | 混合 MRR@10 |
|---|---|---|---|
| 6 / 20 | 0.300 | 1.000 | 1.000 |
| 42 / 48 | 0.229 | 0.979 | 0.908 |
| 187 / 185 | 0.124 | 0.941 | 0.865 |
| **290 / 301** | **0.100** | **0.944** | **0.856** |

**结论**：

1. 语料从 6 项增至 290 项（48 倍），干扰项从 5 个增至 289 个，混合检索 Hit@5 仍保持在 0.94。
2. 关键词检索随规模单调下降（0.300 → 0.100），与混合检索的差距从 0.70 扩大到 0.84。**语料越大，语义路越不可或缺。**
3. 实测事实：**语料正文全部为英文，301 条中文查询几乎无法通过关键词匹配到内容**。混合检索的高指标来自语义路。
4. 这模拟了真实情形——代码与文档是英文，工程师用中文提问。

**必须同时说明的限制**：

1. **语料是有意构造的示例**，不是真实企业资产。
2. **单标注者**：查询与语料出自同一人，存在主观偏置，未做双人一致性检验。
3. **31 条查询只有 1 个相关资源**（占 10%），其余至少 2 个。单一功能类查询（如"判断 IP 在不在网段"）确实只有一个合适资源。
4. **5 项资源未被任何查询覆盖**（占 2%）。
5. **290 项仍是中等规模**，到数千项时会继续下降；Qdrant 切换阈值为 2000 项。
6. **指标不可作为对外宣传依据**（见 §12.2）。

### 7.3 检索延迟

延迟的主要来源不是模型推理，而是**连接建立**。剖析结果：

| 环节 | 优化前 | 优化后 |
|---|---|---|
| 单次远程调用（含 TCP+TLS 握手） | 711 ms | 88 ms |
| 本地计算 | 19 ms | 19 ms |

系统做了三件事：

1. **复用连接**：每个 provider 持有一个长生命周期客户端，不再每次新建
2. **启动预热**：API 启动时完成握手，成本不落在用户第一次查询上
3. **三层缓存**：文档投影、文档向量、查询向量与精排结果

实测（301 条查询 / 290 项语料）：

| 配置 | P95 |
|---|---|
| 无缓存 | 2968 ms（20 查询 / 6 语料基线） |
| 缓存但未复用连接 | 1942 ms（同上） |
| **缓存 + 连接复用 + 启动预热** | **254–428 ms（9 次中 8 次）**、2439 ms（1 次尖峰） |
| **同上，语料扩至 42 项** | 463 ms |
| 语料扩至 187 项 | 525 ms |
| **同上，语料扩至 290 项** | **523 ms** |

达标（目标 ≤ 1.5 s）。语料从 42 项增至 290 项（6.9 倍），延迟从 463 ms 升至 523 ms，涨幅远小于规模涨幅，说明瓶颈仍是网络往返而非索引规模。

**已知限制**：

1. **偶发尖峰无法消除**：远程 provider 偶尔对单条请求响应很慢。属外部服务波动。
2. **预热本身耗时约 0.7 秒**，转移到了启动阶段。常驻服务受益，一次性脚本不受益。
3. **预热依赖 `GET /models` 端点**。某些 OpenAI 兼容服务不提供该端点时，预热失败但不影响功能，首次查询回到旧行为。
4. **缓存收益依赖查询重复度**；无重复时只剩连接复用的收益。
5. **彻底消除网络波动需本地部署模型**，属架构变更，未实施。

## 8. 技术架构

### 8.1 组件

```
┌──────────────┐
│  Web 客户端   │  只调用 API，不直连任何存储
└──────┬───────┘
       │ HTTPS / SSE
┌──────▼────────────────────────────┐
│  API 控制面                        │
│  路由 → 应用服务 → 领域模型         │
└──┬────────────┬─────────────┬─────┘
   │            │             │
┌──▼───┐   ┌────▼─────┐   ┌───▼──────┐
│MySQL │   │Git 内容  │   │检索索引  │
│治理  │   │（只读）  │   │（可重建）│
└──────┘   └──────────┘   └──────────┘
   │
┌──▼───────────┐
│  Worker      │  认领任务、执行确定性校验
└──────────────┘
      ↓ 按需
┌──────────────┐
│ 外部模型服务  │  默认关闭
└──────────────┘
```

### 8.2 基础设施阈值

组件**按规模启用**，不预先堆叠。

| 组件 | 现状 | 启用阈值 | 阈值以下 |
|---|---|---|---|
| MySQL | 必需 | — | — |
| 向量检索 | 进程内矩阵 | 单库 > 2000 个已发布版本 | 当前方案即够用 |
| Qdrant | 未实现 | 同上 | 不需要 |
| Redis | 未实现 | Worker > 4 或需跨机协调 | 数据库行锁轮询 |
| 消息队列 | 未实现 | 需跨机可靠投递 | 数据库任务表 |
| 外部模型 | 可选 | 需语义检索 | 离线哈希（仅验证管线） |

**规则**：配置开关的存在不代表能力的存在。描述组件时必须区分「已实现但关闭」与「未实现」。

### 8.3 存储职责

| 组件 | 是否权威 | 丢失后果 |
|---|---|---|

| 检索索引 | 否 | 重建即可 |
| 缓存 | 否 | 清空即可 |

## 9. 安全要求

### 9.1 凭据

- 凭据**仅**通过环境变量或密钥管理服务注入
- **禁止**写入代码、配置文档、数据库、日志、评测数据
- 未启用的组件不得读取对应凭据
- 缺少凭据时**启动失败**，不降级
- 日志与错误信息中，凭据字段默认**整体删除**而非部分遮盖

### 9.2 不可信内容

资源正文、提示词、工具返回、模型输出、外部仓库内容**都是数据，不是指令**。它们不能改变权限、状态或审批。

### 9.3 输入防护

| 威胁 | 要求 |
|---|---|
| 路径穿越 | 内容访问限定在受管根目录内，拒绝绝对路径、盘符、上级目录、符号链接 |
| 跨租户访问 | 可见性过滤在查询层完成，不可绕过 |
| 越权操作 | 服务端强制校验角色，前端隐藏不构成防护 |
| 注入 | 全部参数化查询 |
| 凭据泄露 | 提交前扫描，历史记录一并审计 |

### 9.4 执行隔离

执行用户代码或第三方工具时，必须：无网络、只读根文件系统、禁止提权、限制 CPU/内存/进程数与超时。

### 9.5 审计

审计日志仅追加，采用哈希链保证完整性。记录：时间、主体、动作、结果、实体与精确版本、关联 ID、原因码。审计中不得出现凭据、完整提示词或未脱敏正文。

## 10. 运行与部署

### 10.1 本地启动

```bash
docker compose up --build
```

> **必须带 `--build`**。`docker compose up` 只复用已有镜像，不会重新构建；源码改动后
> 若省略此参数，容器会继续提供上一次构建的前端产物与后端代码。改动只涉及环境变量时
> 用 `docker compose up -d` 即可，镜像内容不变。

启动顺序：MySQL（执行迁移）→ 种子数据 → API → Worker → Web。

访问：
- Web：`http://localhost:5173`
- API：`http://localhost:8000/v1/health`

### 10.2 配置

所有配置通过环境变量。示例见 `.env.example`。

外部服务默认全部关闭。启用语义检索需要同时设置：

```bash
SUPERCODER_SEARCH_REMOTE_ENABLED=true
SUPERCODER_EMBEDDING_ENABLED=true
SUPERCODER_RERANK_ENABLED=true
SUPERCODER_SEARCH_API_KEY=<从环境注入，禁止提交>
```

### 10.3 容器要求

- 以非特权用户运行
- 镜像基于锁文件构建，保证可复现
- 提供健康检查；数据库就绪判定必须验证真实查询与迁移完成，而非仅进程存活

### 10.4 持续集成

每次推送自动执行：

| 检查 | 内容 |
|---|---|
| 契约校验 | 资源协议、评测格式、数据库模型、API 契约 |
| 单元与集成测试 | 全部测试套件 |
| 前端 | 类型检查与构建 |
| 容器冒烟 | 完整栈启动、健康检查、种子数据验证 |
