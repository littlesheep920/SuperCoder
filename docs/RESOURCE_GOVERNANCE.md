# SuperCoder 资源治理规范

## 1. 目的、范围与规范事实源

本文冻结 SuperCoder Stage 0 对受管 Skill、MCP、Prompt、Agent、Workflow、Tool 的生命周期、运行环境、版本、权限、依赖和审核规则。本文中的“必须”“不得”是强制要求；实现不得以 UI 状态、模型判断、索引结果或人工口头确认替代这些规则。

资源清单的机器值以 `schemas/resource.schema.json` 为准，协议语义以 `docs/RESOURCE_PROTOCOL.md` 和本文共同约束。本文使用大写名称表达治理状态，清单、API 和数据库交换时必须使用对应规范值：

| 治理名称 | `resource.yaml` 规范值 |
|---|---|
| `DRAFT` | `draft` |
| `VALIDATING` | `validating` |
| `PENDING_REVIEW` | `pending_review` |
| `APPROVED` | `approved` |
| `PUBLISHED` | `published` |
| `DEPRECATED` | `deprecated` |
| `RETIRED` | `retired` |

状态属于一个明确的 `(kind, slug, version)`。不同版本必须独立审核和发布；一个版本获批不得使其他版本自动获批。

### 1.1 不可变制品与可变治理状态

`resource.yaml` 的 `status` 是资源当前生命周期的必填治理投影，但不属于已发布业务制品的不可变语义。治理服务或经授权的 Git 工作流保存权威生命周期事件，并只允许按照第 3 节更新清单中的 `status`；除 `status` 外，已发布版本的清单字段、入口及随版本发布的文件均不可变。数据库、API、索引和清单必须由同一治理事件同步，不得各自形成状态真相。发现投影不一致时必须停止转换并以审计事件重建，不能按任一副本静默覆盖。

所有验证、审核、发布和执行记录必须区分两个哈希：

- `artifact_hash`：对规范化 `resource.yaml` 移除 `status` 后的内容，加上入口和全部受管资源文件计算；绑定资源业务契约和不可变制品。同一已发布 `(kind, slug, version)` 的 `artifact_hash` 永远不得变化。
- `manifest_snapshot_hash`：对包含当前 `status` 的完整规范化清单计算；每次合法状态转换后变化，并与转换事件、前后状态和 `artifact_hash` 一起记录。

因此，`PUBLISHED -> DEPRECATED -> RETIRED` 只允许改变 `status` 及外部治理记录，不得改变 `artifact_hash`。若任何其他字段或资源文件需要变化，必须创建更高 SemVer 版本并从 `DRAFT` 重新治理。本文后续所称“候选哈希”“内容哈希”若未特别说明均指 `artifact_hash`。

## 2. 生命周期状态定义

| 状态 | 含义 | 可执行性与可见性 |
|---|---|---|
| `DRAFT` | 所有者正在编写或修订，内容尚未形成验证候选。 | 仅开发或明确授权的预览环境可见；不得被正式 Workflow、推荐或生产执行选用。 |
| `VALIDATING` | 内容被冻结为本轮候选，正在执行 Schema、入口、依赖、权限、安全、适配器和评测检查。 | 只能在隔离验证环境执行，不得向普通用户发布。验证期间任何内容变化都必须回到 `DRAFT`。 |
| `PENDING_REVIEW` | 所有必需自动检查通过，候选等待独立人工审核。 | 只读；不得生产执行或作为已批准资产展示。 |
| `APPROVED` | 指定版本已通过必需审核，但尚未进入公开或受管发布目录。 | 可用于发布前演练；是否允许内部受控执行由平台策略决定，不能等同于 `PUBLISHED`。 |
| `PUBLISHED` | 指定版本已发布，业务制品不可变；仅生命周期 `status` 可按治理事件更新。 | 仅在运行环境兼容、依赖可解析、权限满足且门禁通过时可执行。发布不等于无条件授权。 |
| `DEPRECATED` | 已发布版本仍为兼容迁移暂时保留，但不再推荐新采用。 | 现有固定引用可在策略允许时继续运行并必须产生警告；新依赖默认不得解析到该版本。 |
| `RETIRED` | 版本已退出服务，仅保留审计、回放和历史解析所需记录。 | 不得用于新解析、新执行、新 Workflow 或回滚目标；历史记录不得删除或改写。 |

## 3. 允许的状态转换

### 3.1 转换矩阵

`✓` 表示允许提出转换，但仍须满足本节门禁；`—` 表示禁止直接转换。

| 从 \ 到 | DRAFT | VALIDATING | PENDING_REVIEW | APPROVED | PUBLISHED | DEPRECATED | RETIRED |
|---|---:|---:|---:|---:|---:|---:|---:|
| `DRAFT` | ✓ | ✓ | — | — | — | — | ✓ |
| `VALIDATING` | ✓ | ✓ | ✓ | — | — | — | ✓ |
| `PENDING_REVIEW` | ✓ | — | ✓ | ✓ | — | — | ✓ |
| `APPROVED` | ✓ | — | — | ✓ | ✓ | — | ✓ |
| `PUBLISHED` | — | — | — | — | ✓ | ✓ | — |
| `DEPRECATED` | — | — | — | — | ✓ | ✓ | ✓ |
| `RETIRED` | — | — | — | — | — | — | ✓ |

同状态写入只能作为幂等重放，不得修改资源内容、审核结论或状态时间线。

### 3.2 转换门禁

1. `DRAFT -> VALIDATING`：必须锁定候选内容哈希和精确版本；清单与入口存在；版本此前未发布；验证任务记录创建成功。
2. `VALIDATING -> PENDING_REVIEW`：Schema、路径、类型化字段、凭据扫描、依赖图、权限声明、目标运行环境适配以及该类型要求的契约评测全部通过；结果必须绑定候选哈希。警告不得冒充通过。
3. `VALIDATING -> DRAFT`：验证失败或内容需要修改。必须记录失败项；修复形成新候选后重新执行全部受影响检查。
4. `PENDING_REVIEW -> APPROVED`：达到第 8 节的审核要求，且审核所见哈希与验证哈希完全一致。附条件批准不等于批准，必须回到 `DRAFT` 落实条件后重验。
5. `PENDING_REVIEW -> DRAFT`：审核要求变更、补证或修复；必须保存审核意见，不得删除失败历史。
6. `APPROVED -> PUBLISHED`：批准仍有效，发布目标和运行环境明确，依赖已解析到精确版本，权限与审批策略可执行，发布制品哈希与获批哈希相同，并生成可审计发布记录。
7. `APPROVED -> DRAFT`：发布前发现需修改内容或契约。原批准结论保留为历史但对新候选失效。
8. `PUBLISHED -> DEPRECATED`：必须给出原因、替代版本或无替代说明、迁移指南、警告生效时间和计划退役时间；受影响依赖方必须可查询。
9. `DEPRECATED -> PUBLISHED`：仅允许撤销误弃用或风险已消除，必须由资源所有者和治理审核者共同批准并记录原因；不得改变制品内容。
10. `DEPRECATED -> RETIRED`：迁移期结束，或出现要求立即停止使用的安全、合规、正确性问题；必须完成影响分析并保留解析与审计元数据。
11. `DRAFT -> RETIRED`、`VALIDATING -> RETIRED`、`PENDING_REVIEW -> RETIRED`、`APPROVED -> RETIRED`：允许所有者撤回未发布版本，必须注明未发布撤回原因。该转换不产生发布历史。
12. `PUBLISHED` 不得直接进入 `RETIRED`。紧急停用仍须先原子地标记 `DEPRECATED`，记录 `immediate_retirement` 原因和零迁移窗口，再进入 `RETIRED`，以保留完整状态事件。
13. `RETIRED` 是终态。恢复能力必须创建更高的新版本，从 `DRAFT` 重新治理，不得复活原版本。

任何已发布内容变化都不能通过状态回退完成；必须创建新的 SemVer 版本。

## 4. 运行环境定义与兼容性

清单 `runtimes` 只允许以下规范值：

| 显示名称 | 规范值 | Stage 0 定义 |
|---|---|---|
| Kiro | `kiro` | 由 Kiro 兼容适配器解释资源入口、工具契约和受控工作流的环境。 |
| Claude Code | `claude-code` | 面向 Claude Code 资源表达与工具调用边界的适配环境。 |
| Cursor | `cursor` | 面向 Cursor 项目上下文、规则和工具集成的适配环境。 |
| Dify | `dify` | 面向 Dify 应用、Workflow、知识与工具契约的导入或执行适配环境。 |
| OpenAI-compatible Agent Runtime | `openai-compatible-agent-runtime` | 使用 OpenAI-compatible 模型/工具协议的供应商中立 Agent 运行环境；兼容 API 不代表模型行为等价。 |

`runtimes` 是兼容性声明，不是验证证据。将某环境加入清单前，必须证明该环境的适配器能够无损表达入口、输入、输出、依赖、权限、审批和错误语义，并通过该版本的目标环境验证。缺少适配器、只完成配置转换、依赖或权限在目标环境不可满足、输出无法按 Schema 校验时，必须拒绝兼容声明。

一次执行必须记录资源精确版本、适配器版本、目标运行环境和解析后的依赖。禁止在运行时将未声明环境当作“相近环境”静默回退。运行环境不得读取未显式注入的用户密钥，资源正文中的 Prompt Injection、工具返回或模型输出均视为不可信数据，不能改变系统策略或扩大权限。

## 5. 版本规则

### 5.1 SemVer

资源 `version` 必须使用 SemVer `MAJOR.MINOR.PATCH`，可带标准预发布和构建元数据：

- `MAJOR`：删除或重命名输入输出、增加必填输入、收紧输入约束、削弱承诺输出、改变入口或行为语义、移除运行环境、扩大必需权限、产生不兼容依赖替换等破坏性变化。
- `MINOR`：向后兼容的新能力，例如新增可选输入、增加承诺输出、增加经验证的运行环境或增加不影响既有路径的功能。
- `PATCH`：不改变公开契约的向后兼容修复、文档澄清或安全修复。若修复会改变调用方可观察契约，则不能只升 PATCH。

预发布版本（如 `2.0.0-rc.1`）不得替代稳定版本满足默认依赖范围，除非依赖显式允许该预发布版本。构建元数据不参与优先级，注册表不得仅凭构建元数据区分两份不同内容。

### 5.2 身份、唯一性和不可变发布

- `(kind, slug)` 是资源身份，`(kind, slug, version)` 必须全局唯一并绑定唯一 `artifact_hash`。
- `slug` 变更视为新资源身份；必须通过显式替代关系和迁移说明关联，不能把重命名伪装为普通版本升级。
- `PUBLISHED`、`DEPRECATED`、`RETIRED` 版本的业务制品不可变。清单只允许由合法生命周期事件更新 `status`，并产生新的 `manifest_snapshot_hash`；其他清单字段、入口及随版本发布的文件不得变化。发现错误必须发布更高版本；禁止覆盖、删除、重标相同版本或用 Git 历史改写替换制品。
- 发布记录、审核记录、`artifact_hash`、每个状态的 `manifest_snapshot_hash`、签名/来源、解析后的依赖和评测结果必须保留。索引或数据库可重建字段不得成为内容事实源。
- `DRAFT` 业务内容可以修改；进入 `VALIDATING` 后 `artifact_hash` 被冻结。除合法 `status` 投影更新外，任何资源字节变化都使当前验证和审核失效并回到 `DRAFT`。
- 版本号必须单调演进；已使用的版本号即使未发布后被撤回，也不得被另一份不同内容重用。

## 6. 权限治理

### 6.1 声明和授权分离

权限使用 `namespace:action`，对象形式可带 `scope`、`effect`、`approval_required` 和 `reason`。清单只声明资源需要或禁止的能力，不授予权限。有效权限必须是以下集合的交集：调用者授权、运行环境策略、资源声明、依赖声明和本次审批；任一层缺失即默认拒绝，显式 `deny` 始终优先。

### 6.2 Scope 规则

| Scope | 允许边界 |
|---|---|
| `resource` | 仅当前 `(kind, slug, version)` 的资源目录、制品和运行实例。 |
| `project` | 仅调用时明确选择并授权的单个项目；不得自动扩展到父目录、其他仓库或用户主目录。 |
| `team` | 仅治理系统中明确成员和边界的团队空间；必须有团队级策略授权。 |
| `organization` | 组织范围能力；属于高影响权限，必须有组织级策略和人工审批，不得由资源所有者单独批准。 |
| `external` | 对外部网络、供应商、仓库或系统的访问；必须明确目的、目标类别、数据边界和凭据注入方式。 |

省略 `scope` 不表示无限范围；执行器必须根据权限名和平台策略推导最窄边界，无法唯一推导时拒绝。`approval_required: true` 的操作每次都必须经过对应审批门禁，批准不可跨资源版本、项目、调用者或目标复用。

权限变化规则：删除不再需要的允许权限通常是兼容收紧；新增写入、执行、Secret、组织或外部访问权限必须重新验证和审核；扩大 scope 或将 `approval_required` 从 `true` 改为 `false` 是安全敏感变化，至少升级 MINOR，若破坏既有安全承诺则升级 MAJOR。任何版本不得在清单、入口、示例、日志或评测数据中保存 Secret 值。

依赖不能替父资源获得权限。执行包含依赖的资源时，平台必须计算调用路径上每个节点的最小权限并阻止权限传递升级；子资源的权限需求超出调用者或父执行上下文时必须拒绝，而不是自动授权。

## 7. 依赖治理

### 7.1 版本约束

依赖必须以 `kind`、`slug`、`version` 结构化声明；受管资源按 `(kind, slug)` 解析。`version` 只能是：

- 精确 SemVer，例如 `1.4.2`；
- 受 Schema 支持的明确比较范围，例如 `>=1.2.0 <2.0.0`；
- `*`，仅允许在 `DRAFT` 探索中使用。

`PENDING_REVIEW`、`APPROVED`、`PUBLISHED`、`DEPRECATED` 的发布候选和执行快照必须将所有依赖解析为精确版本并记录。正式 Workflow 不得依赖“latest”、分支名、别名、显示名或浮动 URL。若解析器不支持某范围语法，必须报错，不得按 `*` 处理。

范围选择必须确定且可复现：在满足范围、生命周期可用、运行环境兼容和权限可满足的版本中选择最高稳定版本；不得默认选择预发布、`DEPRECATED` 或 `RETIRED` 版本。锁定结果变化必须触发受影响验证；发布后锁定结果不可原地改变。

### 7.2 必需、可选和外部依赖

- `optional: false` 或省略 `optional` 表示必需依赖。缺失、不兼容、未授权、未获允许生命周期或不可验证时，父资源不可验证、发布或执行。
- `optional: true` 必须有文档化降级行为、可辨识警告和相应测试；缺失时不得静默改变必填输出或安全属性。没有真实降级路径的依赖不得标记为可选。
- `source: managed` 必须解析到注册表中的受管版本。`source: external` 必须绑定可复现来源，如供应商版本加内容哈希、固定提交或镜像摘要；URL 本身不构成版本锁定。
- 外部依赖必须经过来源、许可证、安全、数据传输和可用性审核，不得在解析期间联网下载未知内容或读取用户凭据。

解析器必须拒绝自依赖、同一身份的冲突范围、重复依赖、缺失必需依赖以及依赖环。依赖图中的权限、运行环境和生命周期必须传递检查。某依赖进入 `DEPRECATED` 时，引用方必须收到可查询警告并制定迁移；进入 `RETIRED` 后，不得用于新执行，引用方应被标记为阻塞，直到发布兼容新版本。

## 8. 审核要求

### 8.1 角色分离

每个候选至少包含以下可审计角色：

- `owner`：维护资源，提交候选和修复；不能作为唯一审核者。
- `validator`：执行自动验证并保存工具版本、结果、日志摘要和候选哈希。
- `reviewer`：独立检查用途、契约、内容、安全、权限、依赖、运行环境和评测证据。
- `publisher`：确认批准和制品一致后执行发布；生产发布不得由资源作者在无复核情况下独自完成。

同一人可以承担 validator 的操作职责，但自动结果不能替代 reviewer。涉及 `organization`、`external`、写入、执行、Secret 或高影响审批绕过风险的资源，必须增加安全/治理审核者。Workflow 还必须审核节点可达性、循环/重试、人工门禁、失败补偿和各节点权限；Agent/Prompt 必须审核 Prompt Injection 边界和模型输出不可作为授权证据；MCP/Tool 必须审核执行、网络、文件、超时和返回 Schema。

### 8.2 审核证据与有效性

审核记录必须至少包含资源身份和版本、候选内容哈希、审核者、结论、时间、适用运行环境、自动验证结果引用、权限与依赖摘要、评测证据引用以及意见。允许的结论为 `approve` 或 `request_changes`；静默、评论或附条件意见不构成批准。

以下任一变化都会使现有验证和批准失效：候选内容变化、版本变化、入口变化、输入输出契约变化、权限或 scope 变化、依赖范围/锁定变化、运行环境变化、类型化配置变化，或验证/审核所依据的安全政策发生要求重验的变更。失效候选必须回到 `DRAFT`，不得只补签字。

发布前必须执行最终一致性检查，确认资源哈希、审核哈希和待发布制品哈希相同。任何模型、Agent 或资源所有者均不得自行宣布 `APPROVED` 或 `PUBLISHED`。

## 9. 弃用与退役行为

`DEPRECATED` 版本必须保持 `artifact_hash` 不变；从 `PUBLISHED` 转换时只更新 `status` 投影和外部治理元数据，并提供机器可读或治理记录中的 `deprecated_at`、原因、替代 `(kind, slug, version)`（如有）、迁移说明和 `retire_after`（如可确定）。发现、搜索和 API 响应必须明显标记弃用；解析新依赖时默认排除，已有精确锁定引用执行前必须发出可观测警告。

弃用不能自动改变引用方的锁定版本。迁移必须创建引用方的新版本并重新验证；不得在后台静默替换。若弃用源于安全或合规风险，治理系统可以禁止继续执行，并明确记录阻断原因，而不是仅显示警告。

`RETIRED` 版本必须从新发现、推荐、依赖解析和执行候选中排除，但其清单、制品哈希、审核、发布、使用、评测、弃用及退役事件必须保留供审计和历史回放。历史 Workflow/Job 可以显示当时引用，不得借此重新执行已退役资源。删除数据不是合法退役实现。

## 10. 非法转换和失败处理

所有状态转换必须通过一个原子、带前置状态检查的治理操作完成，并写入仅追加审计事件。请求至少携带资源身份、版本、期望当前状态、目标状态、操作者、原因、`artifact_hash` 和期望 `manifest_snapshot_hash`；高影响转换还必须携带审批记录引用。成功转换必须原子写入新状态、新 `manifest_snapshot_hash` 和审计事件，同时保证 `artifact_hash` 不变。

遇到以下情况必须 fail closed：转换边不存在、前置状态已变化、操作者无权、门禁证据缺失或过期、哈希不一致、审核者不满足独立性、依赖无法解析、权限不可满足、目标运行环境未验证，或目标版本已存在不同内容。处理要求：

1. 返回结构化冲突/验证错误，至少包含错误代码、当前状态、请求目标、失败门禁和可执行的修复方向。
2. 不改变资源状态、内容、版本、锁定依赖、审核记录或索引可见性。
3. 写入拒绝事件，记录请求和拒绝原因，但不得记录 Secret 或未经脱敏的敏感正文。
4. 不得自动跳过中间状态、自动降级权限、静默改写版本范围、自动批准或靠重试最终放行。
5. 并发转换使用乐观锁或等价条件更新；只有一个请求可以从同一前置版本成功，其余返回冲突后重新读取状态。

建议的稳定错误码包括：`INVALID_LIFECYCLE_TRANSITION`、`LIFECYCLE_CONFLICT`、`VALIDATION_REQUIRED`、`REVIEW_REQUIRED`、`REVIEW_STALE`、`CONTENT_HASH_MISMATCH`、`RUNTIME_NOT_VALIDATED`、`PERMISSION_UNSATISFIED`、`DEPENDENCY_UNRESOLVED`、`DEPENDENCY_CYCLE`、`VERSION_IMMUTABLE`。错误码供 API 和 Worker 共用，显示文案不得改变其治理含义。

## 11. 审计与 Stage 0 验收边界

每次候选冻结、验证、审核、批准、发布、弃用、撤销弃用、退役和非法转换拒绝都必须形成事件。事件至少记录资源精确身份、前后状态、`artifact_hash`、转换前后 `manifest_snapshot_hash`、操作者/系统主体、原因、时间、证据引用和关联请求 ID。审计日志只追加且可追溯，不得由资源正文、Prompt、模型或运行时工具改写。

Stage 0 冻结的是正式契约和失败语义，不声称五个运行环境的生产适配已经实现，也不声称示例资源已获企业发布许可。后续 API、数据库、Worker、索引和 UI 必须实现同一状态机；任何实现若允许本文禁止的转换、修改已发布版本、绕过权限交集或浮动解析正式依赖，即不符合本契约。本文变更必须经过架构与治理评审，并同步检查 Schema、资源协议、数据库约束、OpenAPI 和校验器，避免形成多套状态真相。
