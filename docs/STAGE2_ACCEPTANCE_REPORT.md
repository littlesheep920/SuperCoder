## 4. 评测结果

### 4.1 真实语义模型（2026-10-24，已配置 SiliconFlow）

| 指标 | keyword | **hybrid** | semantic |
|---|---|---|---|
| Hit@5 | 0.30 | **1.00** | 1.00 |
| MRR@10 | 0.30 | **1.00** | 1.00 |
| NDCG@10 | 0.30 | **0.9978** | 0.9978 |
| P95 延迟 | 717 ms | **1560 ms** | 3837 ms |

配置：`Qwen/Qwen3-Embedding-0.6B`（1024 维）+ `BAAI/bge-reranker-v2-m3`；语料 6 项，查询 20 条。

### 4.2 这组数字说明了什么

**语义检索确实解决了字面鸿沟**，证据是三档对比：

- 纯关键词 `keyword` 停在 0.30——中文业务语言与英文资源名无共同 token，这是字面匹配的上限。
- 混合 `hybrid` 达到 1.00——RRF 融合让语义召回补上了关键词找不到的部分。
- `semantic` 同为 1.00，但 P95 是 hybrid 的约 2.5 倍——**hybrid 是更优的工程选择**：关键词路提供廉价的精确召回，语义路负责容错。

### 4.3 必须同时说明的限制

1. **6 项语料 + 20 条查询的样本量过小**，Hit@5 = 1.00 不具泛化性；资源规模达到数百项时必然下降。
2. **标注由单人完成**，未交叉验证（PRD §7.3 披露要求）。
3. **查询构造受限于 6 项资源**：每条查询实际只能指向唯一的正确资源，这让"命中"比真实检索任务更容易。
4. **未做 rerank 消融实验**：当前 hybrid 与 semantic 的 NDCG 完全相同，尚不能量化 rerank 的独立贡献。

### 4.4 检索延迟与缓存（2026-10-25 补充）

#### 4.4.1 延迟的真实构成

对 hybrid 查询逐阶段计时（20 条查询、6 项语料）：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 查询向量（远程） | ~666 ms | 每次查询一次网络往返 |
| 精排 Rerank（远程） | ~703 ms | 每次查询一次网络往返 |
| 本地计算 | **~19 ms** | BM25 + 矩阵乘 + RRF 融合，占 1.3% |
| 文档向量构建 | ~933 ms | **旧行为**：每个请求都重建，因为索引属于 per-request 对象 |

结论：延迟的 99% 是**两次远程调用**，本地计算可以忽略。因此优化方向是消除重复的网络往返，而不是优化算法。

#### 4.4.2 已实现的缓存

| 缓存 | 位置 | 键 | 命中率（实测） |
|---|---|---|---|
| 文档投影 | `application/search_service.py` | 版本 ID + `artifact_hash` + 快照哈希 + 更新时间 | — |
| 文档向量 | `search/vector.py` | 模型名 + 嵌入文本 SHA-256 | **98.3%**（354 命中 / 360） |
| 查询向量 | `search/cache.py` | 模型名 + 查询文本 SHA-256 | 66.7%（重复查询全命中） |
| 精排结果 | `search/cache.py` | 模型名 + 查询 + 候选文本序列 | 66.7% |

#### 4.4.3 实测对比

评测脚本支持 `--no-cache` 复现未优化行为。同一批 20 条查询：

| 配置 | P95 | Hit@5 | MRR@10 | NDCG@10 |
|---|---|---|---|---|
| 无缓存（`--no-cache`） | 2968 ms | 1.00 | 1.00 | 0.9978 |
| 缓存，未复用连接 | 1942 ms | 1.00 | 1.00 | 0.9978 |
| **缓存 + 连接复用 + 启动预热** | **279–428 ms** | 1.00 | 1.00 | 0.9978 |

**排名逐条一致**：所有运行的排序结果完全相同，证明这是纯性能改动。

#### 4.4.4 最重要的发现：延迟的主要来源是 TLS 握手，不是模型

进一步剖析发现，每次远程调用都新建 `httpx.Client`，导致**每次都重新做 TCP + TLS 握手**：

| 调用方式 | 单次耗时（6 次测量的中位数） |
|---|---|
| 每次新建客户端 | **711 ms** |
| 复用连接 | **88 ms** |

**单次调用节省 623 ms。** 也就是说，此前测得的"查询向量 666 ms"里，绝大部分是建连开销，而非模型推理。

同样的规律体现在一次完整搜索上：进程内**第一条**查询 1664 ms，其后每条约 230 ms——差别就是两条连接的建立成本。

修复方式：

1. 每个 provider 持有一个长生命周期的 `httpx.Client`，跨调用复用连接
2. 应用启动时主动完成握手（`warm_connection`），把这笔成本移到启动阶段
3. 预热失败只记录日志，不阻断启动

验证（真实环境，非 mock）：

| 场景 | 首次真实调用耗时 |
|---|---|
| 预热前 | 813 ms |
| **预热后** | **107 ms** |

#### 4.4.5 结论：达标，但存在偶发尖峰

8 次独立运行的 P95 分布：

| 运行 | P95 |
|---|---|
| 1 | 279 ms |
| 2 | 281 ms |
| 3 | 308 ms |
| 4 | 314 ms |
| 5 | 329 ms |
| 6 | 346 ms |
| 7 | 412 ms |
| 8 | 428 ms |
| 另一次 | **2439 ms**（尖峰） |

**9 次运行中 8 次在 254–428 ms，达标；1 次出现 2439 ms 尖峰。**

| 场景 | P95 | 目标 ≤1500 ms |
|---|---|---|
| 高频重复查询 | 0.4 ms | **达标** |
| 首次查询 | 254–428 ms（8/9 次） | **达标** |
| 偶发尖峰 | 2439 ms（1/9 次） | 未达标 |

**仍然存在的限制**：

1. **偶发尖峰无法消除**。远程 provider 偶尔对单条请求响应很慢，会把 P95 推高。9 次测量中出现 1 次。这属于外部服务波动，客户端无法根治。
2. **预热本身耗时约 0.7 秒**，已转移到启动阶段。常驻服务受益，一次性脚本不受益。
3. **预热依赖 `GET /models` 端点**。某些 OpenAI 兼容服务不提供该端点时，预热失败但不影响功能，首次查询回到旧行为。
4. **缓存收益依赖查询重复度**；无重复时只剩连接复用的收益。
5. **若要彻底消除网络波动**，唯一办法是本地部署嵌入与精排模型。本机有 GPU（RTX 5060 8GB），但会新增 torch 依赖与数百 MB 模型，属架构变更，未在本阶段实施。

#### 4.4.6 复现方式

```bash
# 生产配置（缓存 + 连接复用 + 预热）
python scripts/run_retrieval_eval.py --profile hybrid

# 对照：关闭缓存
python scripts/run_retrieval_eval.py --profile hybrid --no-cache
```

缓存容量可用环境变量调整，设为 0 即关闭：

```bash
SUPERCODER_SEARCH_QUERY_CACHE_SIZE=256
SUPERCODER_SEARCH_RERANK_CACHE_SIZE=256
SUPERCODER_SEARCH_DOCUMENT_CACHE_SIZE=2000
```

## 5. 实现过程中发现并修复的缺陷

这些缺陷都是在开发中由测试或评测暴露的真实问题，记录以便追溯。

| # | 缺陷 | 影响 | 修复 |
|---|---|---|---|
| D-1 | camelCase 拆分被整体 casefold 破坏 | `resourceVersionId` 塌成单一 token，标识符检索失效 | 先按大小写拆分，再 casefold |
| D-2 | 向量检索无相关性下限 | 任意查询都返回全库，无关查询也像命中 | 增加保守的相似度下限 |
| D-3 | `limit` 在契约中既 required 又有默认值 | 契约自相矛盾，客户端可依赖性受损 | 按 required 严格实现，并在测试中记录该决策 |
| D-4 | `highlights` 未始终输出 | 违反 `SearchHit` required | 始终输出（可为空） |
| D-5 | 评测指标把"无结果"算作命中 | **曾报出 Hit@5=1.0 而实际 0 结果** | 无结果一律记为未命中，并加回归测试 |
| D-6 | 清单类型段键名拼错（`mcp_spec` vs `mcp`） | 四类资源 chunks=0，索引近乎为空 | 提取共享 `extract_type_spec()`，单一事实源 |
| D-7 | 评测资源 ID 与标注格式不一致 | 排名看似正常但全部比对失败 | 统一为 `kind/slug@version` |
| D-8 | 评测 `--out` 指向仓库外时崩溃 | 不可移植 | 相对路径计算失败时回退为绝对路径 |
| D-9 | 校验器按路径加载脚本未注册 `sys.modules` | 使用 `@dataclass` 的脚本被误报导入失败 | 执行前注册、执行后清理，并加回归测试 |
| D-10 | **`str(Secret)` 把 `<redacted>` 当作 API key 发送** | 远程调用全部 401，却被降级逻辑掩盖成"语义不可用"，离线基线看起来正常 | 工厂改用 `Secret.expose()`；加 3 项回归测试；保留 `repr` 脱敏 |
| D-11 | PRD 守护测试未隔离环境变量 | 开发者正常启用远程检索后，本应全绿的测试报错 | 测试内清空受管变量并清除 settings 缓存 |

> D-5、D-7、D-10 都值得单独记录：它们都会产出**看起来正常但完全错误**的结果，而且都被各自的降级或兜底逻辑掩盖过一段时间。这正是 PRD §3.2 坚持"保存原始逐条数据"、以及本报告坚持"降级必须显式上报"的原因。

## 6. 已知限制

1. **真实 API 已验证，但样本极小**：SiliconFlow 调用已实测通过（HTTP 200，1024 维），但只有 6 项资源、20 条查询。
2. **MySQL 持久化路径未覆盖**：检索端点在内存替身上测试，MySQL 可见性谓词行为仍为 HOLD（继承 Stage 1）。
3. **语料仅 6 项**：当前规模下 Qdrant/Redis 无必要（PRD §3.3 阈值 2000），但也意味着检索质量结论不具泛化性。
4. **单标注者**：20 条查询与 25 条标注均由单人完成，**未交叉验证**（PRD §7.3 披露要求）。
5. **查询向量未缓存**：每次检索实时调用 Embedding API，导致 P95 达 1.5–3.8 秒，超出 PRD 季度目标。

### 8.1 禁止使用的表述

| ❌ 禁止 | 原因 |
|---|---|
| "检索准确率 100%" | 6 项资源、20 条查询、单标注者，见 §4.3 |
| "支持百万级资源检索" | 未测试，且当前实现为全量内存索引 |
| "延迟低于 1.5 秒" | P95 实测 1.56–3.84 秒 |
| "生产就绪" | MySQL/浏览器/缓存均为 HOLD |
