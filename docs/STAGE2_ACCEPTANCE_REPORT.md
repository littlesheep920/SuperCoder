## 4. 评测结果

### 4.1 真实语义模型（2026-10-24，已配置 SiliconFlow）

| 指标 | keyword | **hybrid** | semantic |
|---|---|---|---|
| Hit@5 | 0.30 | **1.00** | 1.00 |
| MRR@10 | 0.30 | **1.00** | 1.00 |
| NDCG@10 | 0.30 | **0.9978** | 0.9978 |
| P95 延迟 | 717 ms | **1560 ms** | 3837 ms |

配置：`Qwen/Qwen3-Embedding-0.6B`（1024 维）+ `BAAI/bge-reranker-v2-m3`；语料 6 项，查询 20 条。

### 4.2 这组数字说明了什么

**语义检索确实解决了字面鸿沟**，证据是三档对比：

- 纯关键词 `keyword` 停在 0.30——中文业务语言与英文资源名无共同 token，这是字面匹配的上限。
- 混合 `hybrid` 达到 1.00——RRF 融合让语义召回补上了关键词找不到的部分。
- `semantic` 同为 1.00，但 P95 是 hybrid 的约 2.5 倍——**hybrid 是更优的工程选择**：关键词路提供廉价的精确召回，语义路负责容错。

### 4.3 必须同时说明的限制

1. **6 项语料 + 20 条查询的样本量过小**，Hit@5 = 1.00 不具泛化性；资源规模达到数百项时必然下降。
2. **标注由单人完成**，未交叉验证（PRD §7.3 披露要求）。
3. **查询构造受限于 6 项资源**：每条查询实际只能指向唯一的正确资源，这让"命中"比真实检索任务更容易。
4. **未做 rerank 消融实验**：当前 hybrid 与 semantic 的 NDCG 完全相同，尚不能量化 rerank 的独立贡献。

### 4.4 检索延迟与缓存（2026-10-25 补充）

#### 4.4.1 延迟的真实构成

对 hybrid 查询逐阶段计时（20 条查询、6 项语料）：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 查询向量（远程） | ~666 ms | 每次查询一次网络往返 |
| 精排 Rerank（远程） | ~703 ms | 每次查询一次网络往返 |
| 本地计算 | **~19 ms** | BM25 + 矩阵乘 + RRF 融合，占 1.3% |
| 文档向量构建 | ~933 ms | **旧行为**：每个请求都重建，因为索引属于 per-request 对象 |

结论：延迟的 99% 是**两次远程调用**，本地计算可以忽略。因此优化方向是消除重复的网络往返，而不是优化算法。

#### 4.4.2 已实现的缓存

| 缓存 | 位置 | 键 | 命中率（实测） |
|---|---|---|---|
| 文档投影 | `application/search_service.py` | 版本 ID + `artifact_hash` + 快照哈希 + 更新时间 | — |
| 文档向量 | `search/vector.py` | 模型名 + 嵌入文本 SHA-256 | **98.3%**（354 命中 / 360） |
| 查询向量 | `search/cache.py` | 模型名 + 查询文本 SHA-256 | 66.7%（重复查询全命中） |
| 精排结果 | `search/cache.py` | 模型名 + 查询 + 候选文本序列 | 66.7% |

#### 4.4.3 实测对比

评测脚本支持 `--no-cache` 复现未优化行为。同一批 20 条查询：

| 配置 | P95 | Hit@5 | MRR@10 | NDCG@10 |
|---|---|---|---|---|
| 无缓存（`--no-cache`） | 2968 ms | 1.00 | 1.00 | 0.9978 |
| 缓存，未复用连接 | 1942 ms | 1.00 | 1.00 | 0.9978 |
| **缓存 + 连接复用 + 启动预热** | **279–428 ms** | 1.00 | 1.00 | 0.9978 |

**排名逐条一致**：所有运行的排序结果完全相同，证明这是纯性能改动。

#### 4.4.4 最重要的发现：延迟的主要来源是 TLS 握手，不是模型

进一步剖析发现，每次远程调用都新建 `httpx.Client`，导致**每次都重新做 TCP + TLS 握手**：

| 调用方式 | 单次耗时（6 次测量的中位数） |
|---|---|
| 每次新建客户端 | **711 ms** |
| 复用连接 | **88 ms** |

**单次调用节省 623 ms。** 也就是说，此前测得的"查询向量 666 ms"里，绝大部分是建连开销，而非模型推理。

同样的规律体现在一次完整搜索上：进程内**第一条**查询 1664 ms，其后每条约 230 ms——差别就是两条连接的建立成本。

修复方式：

1. 每个 provider 持有一个长生命周期的 `httpx.Client`，跨调用复用连接
2. 应用启动时主动完成握手（`warm_connection`），把这笔成本移到启动阶段
3. 预热失败只记录日志，不阻断启动

验证（真实环境，非 mock）：

| 场景 | 首次真实调用耗时 |
|---|---|
| 预热前 | 813 ms |
| **预热后** | **107 ms** |

#### 4.4.5 结论：达标，但存在偶发尖峰

8 次独立运行的 P95 分布：

| 运行 | P95 |
|---|---|
| 1 | 279 ms |
| 2 | 281 ms |
| 3 | 308 ms |
| 4 | 314 ms |
| 5 | 329 ms |
| 6 | 346 ms |
| 7 | 412 ms |
| 8 | 428 ms |
| 另一次 | **2439 ms**（尖峰） |

**9 次运行中 8 次在 254–428 ms，达标；1 次出现 2439 ms 尖峰。**

| 场景 | P95 | 目标 ≤1500 ms |
|---|---|---|
| 高频重复查询 | 0.4 ms | **达标** |
| 首次查询 | 254–428 ms（8/9 次） | **达标** |
| 偶发尖峰 | 2439 ms（1/9 次） | 未达标 |

**仍然存在的限制**：

1. **偶发尖峰无法消除**。远程 provider 偶尔对单条请求响应很慢，会把 P95 推高。9 次测量中出现 1 次。这属于外部服务波动，客户端无法根治。
2. **预热本身耗时约 0.7 秒**，已转移到启动阶段。常驻服务受益，一次性脚本不受益。
3. **预热依赖 `GET /models` 端点**。某些 OpenAI 兼容服务不提供该端点时，预热失败但不影响功能，首次查询回到旧行为。
4. **缓存收益依赖查询重复度**；无重复时只剩连接复用的收益。
5. **若要彻底消除网络波动**，唯一办法是本地部署嵌入与精排模型。本机有 GPU（RTX 5060 8GB），但会新增 torch 依赖与数百 MB 模型，属架构变更，未在本阶段实施。

#### 4.4.6 复现方式

```bash

# 对照：关闭缓存

#### 4.6.7 扩充过程如实记录

**未被采用的做法**：曾尝试用模板批量改写已有查询来快速补足数量，产出如下：

```
有没有能做有没有只读的本地资源目录查询工具，不要联网的东西

这些不是真实用户的提问方式。20 条此类变体已全部删除。若保留，查询数会更早达标，但评测会失真——正是 PRD §6 禁止的凑数行为。

**实际采用的方式**：分批新增独立领域（身份与权限、网络、备份、开发者门户、消息队列、架构、数据管道、平台治理、检索运维、告警、SDK 发布、数据产品、安全运营、ML 运维、国际化、沟通），每个领域先补资源，再围绕这些资源写查询。

#### 4.6.8 必须说明的限制

1. **语料是构造的示例内容**，不是真实企业资产。
2. **单标注者**：查询、语料、标注均出自一人，存在主观偏置，未做双人一致性检验。
3. **10% 查询为单答案**（31 / 301）：单一功能类查询确实只有一个合适资源，未强行补充低相关度的第二资源。
4. **5 项资源未被覆盖**（2%）。
5. **290 项仍是中等规模**，到数千项时指标会继续下降；Qdrant 切换阈值为 2000 项。
6. **指标不可用于对外宣传**（见 §8.1）。

### 4.7 能力发现与登记草稿两个通道

#### 4.7.1 为什么先做分数分析

"无证据时拒答"若靠一个分数阈值实现，必须先证明分数能把"有证据"和"没有证据"分开。实测（`docs/RETRIEVAL_SCORE_ANALYSIS.md`，60 条查询）：

| 问题 | 结论 |
|---|---|
| 查询内部，相关结果是否排得更靠前？ | **是**，89.3% 的查询中相关结果分数高于所有不相关结果 |
| 跨查询能否用单一阈值判断有无证据？ | **不能**。无相关结果的查询最高 top-1 为 0.9582，可回答查询最低为 0.0007，完全交叠 |

按阈值拒答会把 94.6% 的可回答查询误拒。**因此拒答改为模型显式判断，并必须列出考虑过的候选。**

#### 4.7.2 发现通道

- 端点 `POST /v1/discovery/recommend`
- 候选由服务端按可见性与生命周期过滤后给出，模型只在其中判断相关性
- 推荐的 `resource_id` / `version` / `artifact_hash` 一律由服务端回填，模型给出列表外的 id 会被丢弃
- 拒答返回 `refusal_reason` 与 `considered`（全部候选 id），可核查
- 问题过于模糊时返回追问

真实模型实测（DeepSeek）：

| 场景 | 结果 |
|---|---|
| 合适的问题 | 推荐 code-review，理由准确，并指出第二个候选的局限 |
| 无关问题（订机票） | 拒答，理由具体 |
| 模糊问题（"帮我搞一下那个东西"） | 拒答 + 2 个追问 |

#### 4.7.3 登记通道

- 端点 `POST /v1/registration/draft`
- **只读**：不写入任何数据，创建资源仍是独立的 `POST /v1/resources`
- 模型输出的 `status` 强制改写为 `draft`
- 校验复用 CI 同一套 `JsonSchemaValidator` 与 schema 文件
- 无模型时返回不可用，不用模板拼凑草稿

**提示词迭代实测**（同一描述，真实模型）：

| 提示词形态 | schema 错误数 |
|---|---|
| 散文式字段说明 | 11 |
| 单一 kind 骨架 | 5 |
| 骨架 + 其余 kind 必需键摘要 | 0（第一次） |
| 加入嵌套枚举（execution_mode 等） | **0（稳定）** |

第二次实测发现模型输出 `execution_mode: "sync"`（不在允许值内），因为提示词只列了顶层枚举。补齐嵌套枚举后通过。

#### 4.7.4 前端

| 页面 | 路由 | 关键行为 |
|---|---|---|
| 智能查找 | `/find` | 拒答以独立面板显示理由与候选清单；推荐附版本与内容哈希 |

## 5. 实现过程中发现并修复的缺陷

这些缺陷都是在开发中由测试或评测暴露的真实问题，记录以便追溯。

| # | 缺陷 | 影响 | 修复 |
|---|---|---|---|
| D-1 | camelCase 拆分被整体 casefold 破坏 | `resourceVersionId` 塌成单一 token，标识符检索失效 | 先按大小写拆分，再 casefold |
| D-2 | 向量检索无相关性下限 | 任意查询都返回全库，无关查询也像命中 | 增加保守的相似度下限 |
| D-3 | `limit` 在契约中既 required 又有默认值 | 契约自相矛盾，客户端可依赖性受损 | 按 required 严格实现，并在测试中记录该决策 |
| D-4 | `highlights` 未始终输出 | 违反 `SearchHit` required | 始终输出（可为空） |
| D-5 | 评测指标把"无结果"算作命中 | **曾报出 Hit@5=1.0 而实际 0 结果** | 无结果一律记为未命中，并加回归测试 |
| D-6 | 清单类型段键名拼错（`mcp_spec` vs `mcp`） | 四类资源 chunks=0，索引近乎为空 | 提取共享 `extract_type_spec()`，单一事实源 |
| D-7 | 评测资源 ID 与标注格式不一致 | 排名看似正常但全部比对失败 | 统一为 `kind/slug@version` |
| D-8 | 评测 `--out` 指向仓库外时崩溃 | 不可移植 | 相对路径计算失败时回退为绝对路径 |
| D-9 | 校验器按路径加载脚本未注册 `sys.modules` | 使用 `@dataclass` 的脚本被误报导入失败 | 执行前注册、执行后清理，并加回归测试 |
| D-10 | **`str(Secret)` 把 `<redacted>` 当作 API key 发送** | 远程调用全部 401，却被降级逻辑掩盖成"语义不可用"，离线基线看起来正常 | 工厂改用 `Secret.expose()`；加 3 项回归测试；保留 `repr` 脱敏 |
| D-11 | PRD 守护测试未隔离环境变量 | 开发者正常启用远程检索后，本应全绿的测试报错 | 测试内清空受管变量并清除 settings 缓存 |
| D-12 | **两个变更端点没有能力映射** | `POST /resources/{id}/versions` 与 `POST /resource-versions/{id}/rollback` 未登记，界面会把它们当成可用动作无条件渲染 | 补 `op:create_version`、`op:rollback`，并在自检脚本中逐个比对"变更端点 vs 能力表" |
| D-13 | `GatedOperation` 与 `Capability` 使用了相同前缀格式 | 代码扫描无法区分两个枚举，自检脚本误报 17 个能力（实际 13 个） | `GatedOperation` 改用 `op:` 前缀，语义上不可能与能力名混淆 |
| D-14 | 文档中测试数已过时（327 / 287） | 读者高估或低估覆盖率 | 更新为 356；自检脚本增加文档数字与真实计数的比对 |

> D-5、D-7、D-10、D-12 都值得单独记录：它们都会产出**看起来正常但完全错误**的结果，而且都被各自的降级或兜底逻辑掩盖过一段时间。这正是 PRD §3.2 坚持"保存原始逐条数据"、以及本报告坚持"降级必须显式上报"的原因。

### 5.1 能力集合接口与界面门控（路线 B）

#### 5.1.1 做了什么

| 层 | 内容 |
|---|---|
| 领域 | `apps/api/domain/capabilities.py`：13 个能力、12 个受控操作、角色谓词 |
| 接口 | `GET /v1/auth/me` 返回身份与能力集合，**不访问数据库** |
| 前端 | `useCapabilities` 组合式函数；登记、删除、回滚、审核、取消任务 5 处入口按能力显示 |
| 治理层 | 角色判定改为调用共享谓词，消除重复规则 |

#### 5.1.2 单一事实源如何保证

能力集合**不是**另写一套规则，而是与治理服务共用同一组谓词：

```python
# 治理服务
if not (is_owner(auth) and is_publisher(auth)):
    raise PermissionDeniedError(...)

# 能力推导
if is_owner(auth) and is_publisher(auth):
    granted.add(Capability.LIFECYCLE_REVERSE_DEPRECATION)
```

两处调用同一个 `is_owner` / `is_publisher`，因此不会各写一遍。

#### 5.1.3 一致性验证（A10 / A12）

| 测试 | 覆盖 |
|---|---|
| 能力与权限双向一致 | **16 种角色组合 × 12 个受控操作 = 192 组断言**，每组比对「能力存在」与「模拟服务端放行」 |
| 单调性 | 增加角色不得减少任何能力 |
| 无孤立能力 | 每个变更能力至少映射一个操作 |
| 端点全覆盖 | 10 个变更端点逐一核对，未门控者须有书面理由 |
| 接口一致性 | `/auth/me` 返回值等于领域推导结果，不做事后加工 |
| 不泄露凭据 | 响应体不含 token |

#### 5.1.4 真实令牌实测

| 令牌 | 角色 | 能力数 | 关键能力 |
|---|---|---|---|
| `dev-owner-token` | owner | 9 | 增删改、提交验证、取消任务 |
| `dev-publisher-token` | owner + publisher | **11** | 额外获得发布与弃用撤回 |
| `dev-reviewer-token` | reviewer | 5 | 审核、完成验证 |
| `dev-validator-token` | validator | 4 | 完成验证 |
| `dev-member-token` | 无 | **3（只读）** | 仅读取 |

弃用撤回**只有同时具备 owner 与 publisher 的令牌才获得**，这条最易写错的合取规则验证通过。

#### 5.1.5 浏览器实测

无头浏览器加载真实控制台，逐种身份检查渲染结果：

| 身份 | 登记按钮 | 提示文案 | 侧栏 |
|---|---|---|---|
| owner | **显示** | — | Demo Owner · owner |
| member（无角色） | **隐藏** | "你的账号没有登记权限" | Demo Member · 只读 |

无 JavaScript 错误。

#### 5.1.6 必须说明的限制

1. **门控只覆盖 5 处入口**：登记、删除、回滚、审核、取消任务。其余读取操作不门控（由可见性过滤负责）。
2. **能力是"可以尝试"，不是"一定成功"**：依赖未解析、审批要求、乐观锁等业务规则仍会拒绝请求。服务端始终是唯一权威。
3. **令牌文件仍是开发用**：`dev_tokens.example.json` 中的令牌仅用于本地与 CI，生产身份认证（OIDC）未开始。
4. **未做前端单元测试**：前端门控通过浏览器端到端验证，没有组件级单测。仓库当前没有前端测试框架。

## 6. 已知限制

1. **语料是示例内容**：290 项中 284 项以 `example-` 前缀和标签标注，描述首句声明其性质；虽形态贴近真实（14 个团队、5 种运行时、含依赖与审批），仍是构造数据，不可作为生产资产引用。
2. **单标注者**：301 条查询与 852 条标注均由单人完成，**未交叉验证**（PRD §7.4 披露要求）；查询与语料出自同一人，存在主观偏置。
3. **10% 查询为单答案**（31 / 301）：单一功能类查询确实只有一个合适资源，未强行补充低相关度的第二资源。
4. **5 项资源未被任何查询覆盖**（2%）。
5. **仍属中等规模**：290 项距离 Qdrant 阈值（2000）很远，指标到数千项时会继续下降。
6. **语料正文全为英文**：301 条中文查询几乎无法通过关键词匹配到内容（关键词 Hit@5 仅 0.100）。混合检索的高指标几乎完全来自语义路。
7. **MySQL 持久化路径未覆盖**：检索端点在内存替身上测试，MySQL 可见性谓词行为仍为 HOLD（继承 Stage 1）。
8. **前端无组件级测试**：仓库没有前端测试框架，界面行为靠端到端浏览器验证。
9. **偶发延迟尖峰**：远程 provider 偶尔响应很慢，多次测量中出现过单次明显高于其余运行的记录。
